# LicenseHub 세션 기록 — 2026-10-06

이 문서는 이번 세션에서 논의·결정·구현된 내용을 정리한다. 관리 UI 정리,
L2 서버 검증 구현, 권한·삭제, 그리고 **응용서비스별 별도 관리 사이트 +
서브 CA 발급 모델** 논의로 이어진다. 마지막 주제는 결론 없이 다음 논의로
남겨 둔다.

## 1. 이번 세션 요약 (결정·구현)

### 1.1 등급: L1/L2만 제공, L3 제거
- L3(Device-Bound)는 기기 식별값을 OS/환경 차이 없이 얻을 방법이 없어
  발급은 되어도 검증이 통과할 수 없는 상태였다.
- `DeviceBinding`, `Certificate.device`, `device_id`(요청·context), `hash_device_id`,
  L3 분기, `DeviceMismatch` 코드를 제거. 등급 범위를 1~2로 제한.
- C 결과 코드 재번호: `CHAIN_INVALID=12`, `CHAIN_TOO_DEEP=13`, `POLICY_REJECTED=14`.
- `licenses.device_id` 컬럼/모델/API 제거(기존 DB 컬럼은 무해하게 방치).

### 1.2 L2 검증 서버 주소를 라이선스별 입력으로
- 이전에는 `LICENSEHUB_VERIFY_URL` 전역값이 기본으로 **LicenseHub 자신**
  (`http://127.0.0.1:8080/api/verify`)을 가리켰다. 배포 앱이 도달할 수 없는 주소.
- `licenses.verification_url` 컬럼 추가, **L2는 발급 시 주소 필수**, L1은 금지.
- 발급 시 그 주소를 인증서 `server.verification_url`에 서명. 환경변수/전역값 제거.

### 1.3 L2 온라인 조회 구현 (실동작)
- 기존에는 core 판정 로직과 `/api/verify`만 있고 **조회 연결이 없어** L2가
  실동작하지 않았다(테스트는 `server_status`를 픽스처에 하드코딩).
- core에 `online` 기능(기본 꺼짐) 추가:
  - `online::fetch_server_status(url, license_id)` — `POST {verification_url}`
    `{"license_id"}` → approved/rejected → `ServerStatus`
  - `online::resolve_server_status(...)` — **Fail-Closed**. 승인만 통과,
    오프라인/오류/형식오류는 `None` → `ServerRequired` → 비활성
  - `online::decrypt_verify_trusted_license_online(...)` — 복호화→조회→검증
  - C ABI `lh_fetch_server_status`, `lh_decrypt_verify_trusted_license_online`
- 요청에 고정 API 키 `x-licensehub-key`를 붙인다. 서버가 검사, 불일치 401.
- `/api/verify`는 blacklist 테이블을 **직접** 확인한다(상태와 무관하게 거부).

### 1.4 L2 정책 확정
- **오프라인 상태에서는 무조건 비활성화**(Fail-Closed). 캐시·grace 없음.
- 만료를 core·서버 두 곳에서 판정하는 것은 허용. 핵심은 **블랙리스트 검증**.

### 1.5 인증 정책·키
- 검증 요청은 고정 API 키 하나(`VERIFY_API_KEY`). 사람이 못 외우도록
  **임의 UUID v4** 값 사용(현재 `a9e54925-1acb-4214-8b2a-38616c561b96`).
- 요청 보안 강화(서명/토큰)는 향후 과제.

### 1.6 사용자·삭제 (admin 권한)
- 이전에는 `role`이 저장만 되고 **권한 검사가 없었다**. `require_admin()` 도입.
- `PATCH /api/users/{id}`: 사용자명·역할·비밀번호 수정(비번 변경 시 세션 폐기).
- `DELETE /api/users/{id}`: 본인·마지막 admin 보호.
- `DELETE /api/licenses/{id}`: 인증서·블랙리스트까지 cascade.
- 블랙리스트 제거도 admin 전용. 감사 로그는 삭제 불가(기록 보존).

### 1.7 관리 UI 정리
- 만료일: 시간 제외, 날짜만. 기본값 오늘+1년. 제출 시 그날 `23:59:59Z`.
- 라이선스 작업 열을 `발급 · 암호화 파일 · 폐기/복구` 3개로 축소.
  키 열(공개키·서명키)·인증서 버튼 제거(앱에 실제 배포되는 건 암호화 파일뿐).
- Application 키는 **생성 시점에 자동 생성**하고 개인키를 그 응답에서 **한 번만**
  내려준다(DB에 저장하지 않음). 입력한 경우엔 생성하지 않음.

### 1.8 바인딩 정리
- C++/C#/Python/Node.js 바인딩·패키징 제거. **C와 Rust만** 유지.
- `packaging/cpp/verify_example.c`는 C 예제라 `packaging/c/`로 이동.

### 1.9 미사용 코드 제거
- Activation Token(`LH-REQ-021`)은 호출처·테스트·C ABI가 전무해 제거.
  (이미지 RS-1~9 밖 후보 항목)
- Challenge-Response는 C ABI·픽스처·테스트에서 실제 사용 중이라 유지.

## 3. 현재 제품 상태

- **등급**: L1(오프라인) / L2(서버 검증). L3 없음.
- **발급물**: `Application 공개키`(입력 또는 자동생성)로 암호화한 `.lic.json` 하나.
- **L2 검증**: 가드가 인증서의 `verification_url`로 조회(Fail-Closed).
- **가드 로직 위치**: `core/`(Rust). C ABI로 노출. 바인딩은 C/Rust.
- **신뢰 앵커**: `core/src/trusted.rs`의 내장 LK2(분산 저장·재조립).
- **서명**: 엔벨로프와 인증서 **둘 다** LH_Pri로 서명, 가드는 둘 다 LK2로 검증.
- **앱 신원**: `application_id = SHA256(Z_Pub)`(언어 무관, 암호학적).
- **호스트 바인딩**: `host_executable_name`/`host_module_name`(Rust 전용, C ABI 미노출).

## 4. 다음 논의 주제 — 응용서비스별 별도 관리 사이트 + 서브 CA

### 4.1 사용자 요구
- 응용서비스(앱)마다 **자체 라이선스·블랙리스트 관리 사이트**를 코드로 제공.
- 앱마다 필요할 때 **정형화된 템플릿**으로 생성·배포.
- **SSH 연결을 제공**하면 대상 서버에 관리 환경을 구축.
- "라이선스허브에서 받은 라이선스를 설정하면 **동등 수준의 라이선스**를
  서비스별로 생성"할 수 있는지.

### 4.2 가능성 평가

| 요구 | 가능? | 근거 |
|---|---|---|
| 앱마다 별도 관리 사이트 | 가능 | 웹앱이 자체 완결형(React+Rust+SQLite+Caddy+systemd) |
| 정형 템플릿 배포 | 가능 | `provision.yml` + `web/deploy/ssh/{bootstrap,deploy}.sh` 존재 |
| SSH로 대상 서버 구축 | 가능 | 이미 그 방식으로 배포 중(현재 단일 인스턴스 하드코딩) |
| 동등 수준 라이선스 서비스별 발급 | **조건부** | 아래 4.3·4.4 |

### 4.3 사용자 가설: "서명된 원문 + 공개키로 재암호화하면 동일하다" → 성립하지 않음

코드 근거:

- `encrypt_license`는 암호화뿐 아니라 **엔벨로프에 LH_Pri 서명**을 붙인다.
  ```rust
  envelope.signature = URL_SAFE_NO_PAD.encode(issuer.signing_key().sign(&payload).to_bytes());
  ```
- 가드는 `decrypt_license`에서 **엔벨로프 서명을 LK2로 검증**한다.
- 따라서 LIC에는 서명이 두 겹(엔벨로프 + 인증서)이고, 서명된 인증서와
  공개키만으로는 새 엔벨로프 서명을 만들 수 없다.
- 게다가 재암호화는 **같은 인증서**(특정 `application_id`에 묶임)만 재현한다.
  소유자·만료·등급을 바꾸거나 다른 앱용을 만들려면 **새 인증서를 서명**해야 한다.

결론: 자식이 "동등 수준"으로 발급하려면 **가드가 신뢰하는 서명 키**가 필요하다.

### 4.4 세 가지 모델

- **A. LH_Pri 공유** — 자식이 루트 개인키를 그대로 사용. 가장 단순하지만
  루트 키를 배포하므로 하나만 유출돼도 전체가 무너진다. 비권장.
- **B. 서브 CA 위임(정석, 미구현)** — 부모가 자식 키에 **위임 인증서**를
  서명해 주고, 자식은 자기 키로 인증서·엔벨로프를 서명. 가드는 루트 LK2로
  "자식 서명 + 부모 위임"을 검증. 엔벨로프의 `key_id`로 위임 키를 식별 가능.
  ```
  부모: Delegation = Sign(root_LH_Pri, {child_pub, scope, expiry})
  자식: LIC = Sign(child_key, cert) + Encrypt(app_Z_Pub)
  가드: root LK2 로 (1) child 서명 검증 (2) Delegation 검증
  ```
- **C. 중앙 발급** — 자식은 UI/테넌트일 뿐, 서명은 부모 API가 수행. 가장 안전,
  자식은 부모에 의존.

### 4.5 현재 코드에 없는 것
- `sub-ca` / `tenant` / `delegation` 개념 0건.
- `Certificate.children` 체인은 있으나 **부모·자식이 같은 키로 서명** → CA 위임 아님.
- 위임 인증서 포맷, 위임 발급 API, 위임 폐기(delegation revocation) 없음.

### 4.6 보안 함의
- B/C 모두 **자식이 검증 서버를 통제**하면 자기 라이선스를 항상 approved로
  답할 수 있다(자식=제품 주인이므로 예상된 일). 부모가 자식을 통제하려면
  부모가 검증 경로에 있거나 위임을 폐기할 수 있어야 한다.
- 블랙리스트는 자식 DB에 있어 **자식별 독립**. 부모의 폐기가 자식 라이선스에
  전파되려면 위임 폐기를 별도 설계해야 한다.

## 5. 다음 논의를 위한 열린 항목

1. **발급 권한 모델 확정**: B(서브 CA) vs C(중앙 발급). — 최우선 결정
2. **서브 CA 스펙**(B 선택 시): 위임 인증서 포맷, scope(앱/제품/기간),
   키 회전, 위임 폐기, `key_id`→위임 해석.
3. **코어 검증 확장**(B 선택 시): 리프 서명을 자식 키로, 자식 키 정당성을
   부모 위임으로 검증하는 경로.
4. **템플릿·SSH 프로비저닝 일반화**: 인스턴스명·서명키·도메인·GitHub repo·
   부모 라이선스를 파라미터화.
5. **요청 보안 강화**: 고정 키 → 요청 서명/토큰, 키 난독화(추출 저항).
6. **언어별 앱 신원(RS-7)**: 실행 파일 이름은 별도 DLL·해석 언어(Python/Node)에서
   무의미. 언어별 코드/패키지 신원(C# assembly, Python distribution, Node package,
   C/C++ build-id) 전략 필요. `host_*` C ABI 노출 여부.
7. **웹서비스 시나리오**: 호스트/기기 바인딩 제외, `application_id` + 배포 신원
   + L2 온라인 검증. 허용 인스턴스 수·하트비트 필드 검토.
8. **L3 재도입 여부**: 생성형 설치 ID + 등록 API를 갖추면 가능. 현재는 보류.
