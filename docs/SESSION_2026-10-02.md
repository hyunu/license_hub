## 1. 웹앱 개선 (프론트/백엔드)

### 1.1 공개키 다운로드
- 각 라이선스 행에 **공개키** 버튼 추가 → 해당 인증서가 사용한 `.pem` 다운로드.
- 백엔드: `certificates` 테이블에 `key_id`·`public_key` 컬럼 추가(마이그레이션 포함).
  발급 시점의 공개키를 이력에 저장 → **개인키가 교체되어도 이전 인증서의 검증 공개키를 추출 가능**.
- 엔드포인트:
  - `GET /api/public-key/download` — 현재 키
  - `GET /api/certificates/{license_id}/public-key[/download]` — 인증서별 사용 키
- **문제**: 이전 버전에서 발급된 인증서는 `public_key` 이력이 없어 404.
  → 이력에 없으면 **현재 서명 키의 공개키로 대체**(동일 `license-signing-key`)로 해결.
- `Issuer::key_id()` 접근자 추가.

### 1.2 좌측 사이드바 접기
- 접히면 폭 218px→56px, **아이콘만 표시**.
- **수직 중앙의 둥근 토글 버튼** (chevron: 펼침=좌향/접힘=우향).
- 접힘 상태: 브랜드=마크만, 내비=아이콘만(title 툴팁), 하단=로그아웃 아이콘만.

### 1.3 토스트 자동 소멸
- 모든 액션 알림을 우상단 고정 토스트로 전환, **4.2초 후 자동 소멸** (`toast.tsx`).
- Licenses/Blacklist/Users/Dashboard/Audit/Sync 적용. 로그인 폼 오류만 유지(재시도 전까지).

### 1.4 인증서 컬럼
- 원인: 백엔드가 발급 인증서 수를 내려주지 않아 항상 `—`.
- 해결: `License.certificates`(발급 횟수) 서브쿼리 추가. 표시: 미발급=`—`, 발급=`1회`…, L3+device=`bound`.

### 1.5 다운로드 404 (인증서 미발급)
- 원인: **인증서가 발급되지 않은** 라이선스에서 다운로드 → 404 `no certificate issued`.
  (예: YDM5-SK27은 `—`, Q2VX-97UL·V5WH-VZ8B는 발급됨)
- 해결: `certificates === 0`이면 다운로드 버튼 **비활성화** + 툴팁/안내 토스트.
- **보기** 버튼 추가: 발급 시에만 보이던 인증서 JSON을 언제든 다시 조회(`GET /api/licenses/{id}/download` 재사용).

## 2. 라이선스 보호 설계 (코어)

### 2.1 핵심 목적
> 코어로직(라이브러리)이 **승인된 응용SW A에서만** 동작하게 하고, 코어를 복사해
> 무분별하게 다른 응용SW를 만드는 **재사용을 막는** 것.

### 2.2 기본 원칙
- **라이선스(앱 정보)와 서명 = 한 인증서에 함께.** 분리하면 결합·위조 여지.
- **공개키는 인증서에 넣지 않고 별도 신뢰 경로**로 배포 (인증서에 넣으면 라이선스+서명+키 동시 교체 가능).
- **위협 모델**: 순수 클라이언트(오프라인)로 **전체 설치본 복제는 막을 수 없음**.
  클라이언트가 막는 것은 (a) 라이선스 파일 단독 공유, (b) 코어로직의 다른 앱 재사용(무분별한 재사용).
  결정적 공격자(패치/우회)는 하드웨어 앵커(TPM) 또는 서버 활성화 필요.

### 2.3 X / Y 케이스
| | X | Y |
|---|---|---|
| 내용 | `A설명`(제품명·버전·빌드해시) + K1 서명 | `A공개키` + K2 서명 |
| 검증 키 | 코어 내장 K1 (분산 저장) | A에 배포된 CA 인증서(K2) |
| 용도 | 응용SW 핵심로직 방어 | 응용SW 활성화 / 서브CA 승인 |

- 케이스1 = X만, 케이스2 = Y만, 케이스3 = X+Y.
- X는 **제품 단위**(정품성·코어 방어), Y는 **설치/키 단위**(활성화). "특정 설치/장치 전용"은
  X만으로 불가능 → L3 장치 바인딩 또는 Y와 조합.

### 2.4 체인의 두 축
1. **등급 체인** (`Certificate.children`) — 응용SW 활성화(2차) → 코어로직(1차).
   자식 하나라도 실패 → 전체 실패(`ChainInvalid`) → 코어로직 차단. **이미 구현**(`max_chain_depth` 기본 3).
2. **키 체인**(루트 키 → 서명 키) — 루트가 서명 키 공개키를 승인(키 인증서). 키 회전·위조 방지.
   **미구현** (구현 시 `Certificate.public_key` 필드 + 2단계 검증 필요).

### 2.5 인증서 포맷
- **X.509가 아닌** 커스텀 JSON + Ed25519 (`schema_version: 1`).
  사람이 읽을 수 있고 등급·장치바인딩·자식체인 등 커스텀 필드에 적합.

### 2.6 내장 신뢰 공개키 (K1)
- `core/src/trusted.rs`: 32바이트 키를 **4조각 + 마스크(XOR) + 순서 셔플**로 분산 저장,
  사용 시점에만 재조립 → 정적 분석으로 평문 키 직접 발견 어려움.
- **무결성 검증**: 재조립 키의 SHA-256이 `KEY_SHA256`과 다르면 panic(fail closed).
- **zeroize**: 재조립 버퍼를 사용 직후 0으로 덮어씀.
- **`verify_trusted(cert, ctx)`**: 키를 함수 밖으로 노출하지 않고 재조립→검증→파기.
  X 케이스는 키가 **검증 순간에만 메모리에 존재**.
- C ABI: `lh_trusted_public_key`, `lh_verify_trusted_certificate` (바인딩 C/C++/C#/Python/Node 반영).
- 도구: `cargo run --example gen_trusted_key` — 새 K1 생성 또는 공개키 입력으로 분산 상수 출력.

### 2.7 X 발급 API
- **`Issuer::issue_x(AppIdentity)`**: 앱 이름(제품명·버전·`product_id`·`executable_name`)을
  입력받아 K1 개인키로 서명. 발급 직후 내장 K1 공개키로 자체 검증해 **K1이 아닌 키로
  서명하면 오류 반환**(잘못된 키 차단).

### 2.8 호스트 바인딩 (X의 "해당 A에서만")
`VerificationContext`의 바인딩 값을 서명된 X 필드와 대조, 불일치 시 `PolicyRejected`:

| 바인딩 | 출처 | 리빌드 | 비고 |
|---|---|---|---|
| `product`/`version` | 프로젝트 파일 | 불변 | 기본, 개발 무중단 |
| `product_id`(GUID) | 프로젝트 파일 | 불변 | 앱 단위 구분 강화, 서명 metadata |
| `executable_name` | `host_executable_name()` (`current_exe`) | 불변 | 단독 exe용 |
| 모듈(DLL) 이름 | `host_module_name()` (`dladdr`/`GetModuleHandleEx`) | 불변 | 응용SW 로직을 DLL로 분리 시 |

- **개발 편의**: 빌드해시를 쓰지 않으므로 **리빌드와 무관**. 버전 생략 시 제품명만 대조.
- **재사용 방지**: 코어를 다른 앱 B에 임베드 → B의 제품명/고유값/실행파일 이름 ≠ X → 거부.
- 서명 대상: `metadata`(product_id/executable_name) 포함 전체 canonical화 — 바인딩 값이 암호학적으로 보호됨.

### 2.9 "특이점"이란 무엇인가
- 코어는 라이브러리라 호스트 파일을 직접 못 읽음 → **호스트가 자신의 정체성을 등록하고
  코어가 X의 서명값과 대조**하는 형태.
- 실행 파일/모듈 이름은 코어가 스스로 측정할 수 있는 유일한 값 → 가장 강한 바인딩.
- 언어별 프로젝트 파일 = 정체성의 표준 출처 (Cargo.toml/package.json/csproj/CMake).

## 4. 남은 과제 (Open Items)

1. **Y 케이스·키 체인**: `Certificate.public_key` 필드 + 루트→서명 키 2단계 검증 (미구현).
2. **백엔드 발급 연동**: 관리자 API가 `issue_x`를 호출해 X 인증서(제품명·GUID·실행파일명)를
   발급하는 엔드포인트 (core는 지원, 백엔드 연결은 안 됨).
3. **운영 K1**: 현재 굽힌 키는 데모용. 운영 시 `gen_trusted_key`로 재생성·굽기 필요
   (개인키는 서버 시크릿, 커밋 금지).
4. **바인딩 정체성 확장**: 설치 토큰(플랫폼 독립), 기기 ID(하드웨어 귀속, OS별 구현) — 필요 시.
5. **전체 복제 방어**: 순수 클라이언트로 불가 → 하드웨어 앵커(TPM) 또는 서버 활성화 검토.
